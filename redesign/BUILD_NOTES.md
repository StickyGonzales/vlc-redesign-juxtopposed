## 2026-10-13 performance: settings sidebar effects and the resume lookup (worktree, not built yet)
- Settings sidebar sliders did UI-thread work that scales with the page, not with the change: about 100 bindings read `(RdEffects.revision, RdEffects.xxx(...))`, every setter (each step of a drag) bumped the one revision, and each binding then took the player lock (getVout / getAout), read vout / aout variables and the configuration and parsed strings on the UI thread. config_SaveConfigFile also ran on the UI thread 500 ms after the last change (5-50 ms, possibly mid-drag). Fix: RdEffects caches every value in a QQmlPropertyMap (`RdEffects.values`), one property per key, so a binding follows only its own value and reads it without a lock: `RdEffects.values[RdEffects.videoKey("hue")]`; the ...Key() functions read a value from VLC the first time it is asked for; equalizerPreset, equalizerBands, subtitleTextScale and subtitleDurationFactor always exist. A setter updates its cached value at once and queues the change; queued changes reach VLC in call order, at most once per frame (16 ms, consecutive steps of the same change merged), then the values they touched are read back from VLC. The cache is re-read by refresh(), when the video outputs change and when a sidebar page is shown. The file is saved on a worker thread (config_SaveConfigFile is serialized by its own static lock and reads values atomically under RCU, src/config/file.c); string options set during a save are held back until it ends, since config_PutPsz calls vlc_rcu_synchronize and would wait for it. The destructor applies the last queued changes and waits for the save; VLC writes the file again when it quits (config_AutoSaveConfigFile).
- Compatibility: option(), the other getters, setOption(), optionChoices(), optionRange(), optionDescription(), refresh() and `revision` keep working; the getters return the cached values and `revision` changes once per apply and on refresh() (no binding of this branch reads it any more). The Video, Audio and Subtitles sidebar pages and the Settings dialog's Subtitles page now use the per-key form. Other branches should migrate `(RdEffects.revision, RdEffects.option(n))` to `RdEffects.values[RdEffects.optionKey(n)]`.
- Checked offscreen with PySide6 6.8.3 before any build: a QQmlPropertyMap key inserted from a Q_INVOKABLE called inside the binding that reads it gives a working per-key dependency (only that binding re-evaluates; keys added later, from later components, also work).
- Resume prompt: the redesign's resume position lookup (vlc_ml_get_media_by_mrl, SQLite) ran on the Qt main thread at every file open. It now runs through MediaLib::runOnMLThread and the prompt state is set in the UI callback (the toast appears once the position and the 20 s rule are known, as before); a query whose media was replaced or stopped meanwhile is ignored (m_restoreQuery).
- To check on the build: drag every sidebar slider (equalizer bands and preamp, compressor, video adjust, subtitle duration, font size) with QSG_RENDER_TIMING=1: 60 fps, the effect follows live; Flip None / Horizontal / Vertical and Rotate; toggling filters on and off, Wall then Clone (one splitter at a time); equalizer preset then a band, None then a band (turns the equalizer on); settings survive a restart; change a value in VLC's Effects dialog, then open the sidebar page (shows the new value); open files with and without a saved position, and one watched to its last 20 s; quickly switching files does not show a stale prompt.

## 2026-10-15 bug: subtitle speed / timing froze the video, audio kept playing (worktree, not built yet)
- Sticky: "when changing subtitles speed and timing it freezes the video but the audio keeps playing".
- Cause (core path, read in the source): "Subtitle Speed" is VLC's sub-fps (vlc_player_SetAssociatedSubsFPS, player.c:1209, INPUT_CONTROL_SET_SUBS_FPS, RequestSubRate input.c:974). For an external subtitle file with a video that reports its fps (mp4, mkv, avi) every new value changes slave_subs_rate, and SlaveDemux (input.c:3145) then sends ES_OUT_RESET_PCR: EsOutChangePosition (es_out.c:1161) flushes every decoder, video and audio included, resets the clocks and rebuffers. The audio restarts after a few ms; the video decoder starts again from inter frames and has nothing clean to show until the next keyframe (frozen or smeared picture for up to a GOP). The sidebar slider set the fps on every mouse move, so a drag kept the video frozen. Stock VLC does the same once per spin box step (Adjustments and Effects > Synchronization > Subtitle speed).
- Subtitle Track Delay: the core path is cheap (vlc_player_SetCategoryDelay > es_out SetDelay > decoder delay > vout_ChangeSpuDelay > SPU channel clock delay; no flush, no rebuffer; a negative delay only raises the input pts delay). Still sent on every mouse move with an OSD text each time: now at most every 100 ms while dragging and on release.
- Subtitle Duration Factor: subsdelay-factor is a command variable of the subsdelay sub filter, proxied by the vout (filter_AddProxyCallbacks): live, cheap. Crossing 0 during a drag switched the filter off and on (sub-filter chain rebuilt on the next subtitle, displayed subtitles lose their extended duration). Not a video stall, but now the filter is switched off only when released at 0.
- Mapping and labels (Sticky's screenshot: "1.000 fps", thumb at the far left; Duration Factor "0.000" far left): correct and as in the video 7:16-7:23 (rows 92/94: "Subtitle Speed 1.000 fps", "Subtitle Duration Factor 0.000", both thumbs at the far left) and VLC's Synchronization tab: sub-fps is the frame rate the subtitle file was timed for (1 to 100 fps), and 1 fps (or less) means the file's own timing, so the default sits at the left end. Decision 48 (two profiles) and Decision 49 (Cone logo approved, Q6). Branch work/brand, pushed as wip/brand-layer; not built yet.

**Design.** One build input picks the profile and everything else follows from it:
- GitHub: Actions > build-windows > Run workflow > "Brand profile" (vlc / public; default public and pushes build public since Decision 50). The workflow passes it as `VLC_BRAND` into the build container and calls `extras/package/win32/build.sh ... -B "$VLC_BRAND"`; the public artifact is named `vlc-redesign-win64-public`.
- build.sh `-B <profile>` adds `--with-brand=<profile>` (autotools, what CI uses) and `-Dbrand=<profile>` (meson).
- configure.ac `--with-brand=vlc|public` / meson_options.txt `brand` (combo) + root meson.build `brand_profiles`: the packaging values (table below), `VLC_BRAND_PUBLIC` in config.h (config.h.meson) and the automake conditional `BRAND_PUBLIC`. Profile "public" stops configure / meson with a clear message when a logo file is missing or an in-app SVG lacks the #FF8800 accent slot; profile "vlc" needs none of the files.
- modules/gui/qt/util/brand.hpp: the one definition of what the interface shows (name texts, logo names, seasonal cones); util/brand.cpp: the icons (`brand::windowIcon`, `trayIcon`, `trayMenuIcon`, `aboutLogo`, `extensionFallbackIcon`) and the QML singleton `Brand` (VLC.MainInterface: isPublic, name, shortName, title, welcomeTitle, welcomeText, logoIconSmall / logoIcon / logoIconLarge, logoSvg). The texts are macros so `qtr()` looks up VLC's exact source strings (and their translations) in the vlc profile.
- Assets: modules/gui/qt/pixmaps/brand/public/ (cone-logo.svg master, cone-logo-16.svg, cone-logo-24.svg, cone-16/24/32/48/64/128/256.png) through modules/gui/qt/brand_public.qrc (only built with BRAND_PUBLIC: Makefile.am `brand_public.cpp`, meson `qrc_files`), and extras/package/win32/brand/public/ (cone.ico 16-256 for the exe, file icons and installer; cone-tray.ico 16-48). The vlc profile keeps VLC's own files (share/icons, pixmaps/misc/cone.svg, pixmaps/redesign/vlc.svg); no brand/vlc folder is needed.
- Logo color: the in-app SVGs fill the logo with **#FF8800**, the accent slot of the SVG colorizer (util/color_svg_image_provider.cpp `COLOR_ACCENT_KEY` / `_res_ACCENT`, the same slot pixmaps/redesign/vlc.svg uses). RdIcon (`qrc:///rd/<name>.svg`, `.accent(...)`) and the plain images (`SVGColorImage.colorize(Brand.logoSvg).accent(...)`) replace it with Dark/Accent/Logo (`VLCStyle.palette.rdAccentLogo`, #D37918 at the default accent), so the logo recolors live with the accent exactly like the cone. Any other color in those files stays fixed. The PNG / ICO files are fixed #D37918 (window, taskbar, tray, About, exe, installer: system icons, like VLC's cone).
- Qt has no ICO reader in VLC's build (only the SVG and JPEG image plugins), so the interface loads the PNGs; they are byte for byte the entries of cone.ico and cone-tray.ico.

## 2026-10-15 waveform scan hang on MP3 (HIGH, build 38800817536; fix not built yet)
- Bug: with a 3 min 192 kbit/s MP3 playing, switching Playback > "Show Waveform on Seekbar" on showed no waveform, the log had no "waveform scan" / "waveform: ready" line, and Ctrl+Q left VLC "Not responding" (about 167 s of CPU, force-closed).
- Cause: `RdWaveformScanner::Scan::process()` (rd_waveform_scanner.cpp, the packetizer loop) released the input block after `pf_packetize()` and in its two error paths. A packetizer owns the block it is given: a bytestream packetizer (MPEG audio, also AAC, FLAC, A52 ...) pushes it into its queue and leaves `*pp_block` pointing at it, and the input core never releases it. So every MP3 block was freed while still queued: a use after free / double free that corrupts the packetizer's block chain; the next block of the same size reuses the freed memory, the chain loops on itself and the packetizer spins forever inside `pf_packetize()`, where the scan's cancel and stop checks are never reached. The scan never ended (no log line, no bars), and `~RdWaveform` waited for it with an unbounded `QThreadPool::waitForDone()` on the GUI thread: the hang on quit. The PC tests of the branch used WAV and PCM-in-MOV only, whose copy packetizer clears `*pp_block`, so they never hit it.
- Fix: `process()` never releases the block it hands the packetizer (as the core's decoder loop) and always lets the packetizer finish the block; once the scan stops (cancel, failure, time budget), packets are dropped instead of decoded. A hard time budget of 60 s per scan (`RdWaveformScanner::kTimeBudgetSeconds`, checked at every packet and decoded frame; over it the file gets no waveform, cached like an unusable file). `~RdWaveform` waits at most 500 ms (`kQuitWaitMs`) for a cancelled scan, then leaves the pool to the process's end with a warning instead of hanging; the scan's VLC objects now hang from the libvlc instance, which outlives the interface. New log line `waveform: job started for the playing file` when the job starts, so a test shows whether the option reached the scanner.
- Checked by reading: the option turned on mid-playback starts the job at once (acquire() -> startScan(), the length is already known), but only for a thick seek bar (control bar time text Inline); the scan runs on the pool thread only; cancel sets the flag and kills the scan's VLC interrupt.   - The rwlock (same values in all three): 1 reader in, none out. Its only reader is `_pthread_cleanup_dest`, which runs a thread's key destructors at its exit, holding the read lock, in key creation order.
  - winpthreads' thread records: the main thread, and the Qt GUI thread `vlc-qt` with both key values already cleared but its record and thread handle never released: its exit cleanup started and never finished, yet the thread ended normally (exit code 0) about 1.1 s before ExitProcess. Key 0 is libgcc's emulated TLS (emutls: `emutls_destroy` frees the thread's thread_local storage), key 1 libstdc++'s thread_local destructor list. Left in the heap: vlc-qt's 2-entry destructor list (Qt thread_locals registered from QtCore and from the animation timer code), whose first object pointer points into unmapped memory in all three processes.
- Cause: with this toolchain (VideoLAN's win64-posix image: GCC 14 mingw, static libstdc++ and winpthreads in the plugin) an exiting thread frees its thread_local storage (emutls key, created first) before it runs the destructors of its thread_local objects (libstdc++ key, created second). For vlc-qt, Qt's thread_local destructors run on freed memory; when those pages are already unmapped the destructor faults inside the thread's TLS callback, the loader swallows the fault and the thread ends with winpthreads' key lock read locked. At process exit libstdc++ deletes its key from the plugin's DLL detach code and waits for that lock forever. Whether the freed pages are unmapped depends on the heap state at quit, hence the intermittent hits (why the sessions with audio hit it is not proven; the memory freed by the interface's teardown differs). Not the waveform: the FLAC run's scan had finished (its cache file is written 2 s after start) and its worker pool thread had ended long before the quit.

Harmless with native TLS or a C runtime `__cxa_thread_atexit_impl` (the first registration only comes earlier).

A cancelled scan stops within one demuxed packet (VLC interrupt).

- Bug (MED, found on Windows): pasting a playlist link (e.g. a local http://127.0.0.1/.../index.m3u) left "Playlist Name (optional)" empty (the video fills in "Index" at 13:17), and Save with the name left empty played the streams instead of saving a stream list under Network. Cause: OpenNetworkStreamDialog.qml filled in no name and only saved stream lists when a name was typed; without one every link went to the playlist to play.
- Fix: the name fills in from the first playlist link (m3u, m3u8, pls, xspf, asx): its file name without the extension, first letter upper case (RdStreamListSaver.autoName); empty when the link has no file name. It follows the links until the user types a name; a typed name is never overwritten, and clearing it lets it follow the links again. Save now always saves playlist links as stream lists under Network: under a typed name (several links: "<name> 1", "<name> 2", as before), otherwise each under the name from its own link, its host name when the link has no file name, or "Network Stream".
- Kept (existing design, W6.4): links that are not playlists play when no name is typed (a single stream link plays like Open URL, several play as a queue) and are saved as a media library playlist under a typed name. With a playlist link and plain links mixed and no typed name, the playlist links are saved and the plain links play.
## 2026-10-25 New Playlist dialog: the file's name instead of "Library item" (P6-17, wip/fix-new-playlist-names)
- Bug (LOW, found on Windows, 0.2.0 build 39477088729): library file "..." > Add to Playlist > New Playlist... listed the file in "Select Files" as "Library item" instead of its name; the saved playlist was right. Cause: the file menu hands the dialog the media library ids (MLItemId), and RdPlaylistDialog only knew names for URLs.
